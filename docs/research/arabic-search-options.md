# Arabic-capable search options (Pagefind's exact-match gap)

Research date: 2026-08-24. Resolves [issue #7](https://github.com/kihonq/qurescent/issues/7), a child of the wayfinder map ([issue #1](https://github.com/kihonq/qurescent/issues/1)).

Scope: `docs/research/starlight-capabilities.md` already established that Starlight's built-in Pagefind indexes Arabic text but has **no stemming for Arabic** ("Pagefind's published language-support matrix lists Arabic (`ar`) as supported for Word Stemming: ❌", per that doc's §5, citing [Pagefind: Multilingual](https://pagefind.app/docs/multilingual/)). This document does not re-litigate that finding; it surveys what else exists — Fuse.js, MeiliSearch, Typesense, Lunr.js, and Quran-specific tooling — against three questions the map's constraints force for each: (a) does it actually understand Arabic morphology/diacritics, with a citation; (b) can it run as a client-side index in a fully static build (the map's hard constraint — "fully static build, no SSR/live per-request API calls"), or does it require a live server; (c) rough cost, given the project's stated "no monetary motive... prefer free/low-cost, low-maintenance choices."

All claims are sourced from each tool's own docs, source repo, or GitHub issue tracker — not third-party roundups — with one explicitly-flagged exception (Tarteel, §5) where no official primary source exists and third-party reimplementations were used instead.

---

## 1. Fuse.js (already in use today, for surah-name search)

Qurescent's `src/pages/index.astro` already imports `fuse.js` and fuzzy-matches surah metadata (`id`, `name`, `englishName`, `englishNameTranslation`) client-side with `threshold: 0.2`. The question is whether the *same library* could reasonably extend to full verse text + translations.

**(a) Arabic/diacritic capability:**

- Fuse.js ships an explicit `ignoreDiacritics` option: "When `true`, comparisons ignore diacritics (accents). For example, `é` matches `e`." — [Fuse.js docs: Fuzzy Search, `ignoreDiacritics`](https://www.fusejs.io/fuzzy-search.html)
- This is not just a Latin-accent feature. Reading the actual implementation (`src/helpers/diacritics.ts` in the `krisk/Fuse` repo), `stripDiacritics` NFD-normalizes the string and then strips a Unicode combining-mark range that explicitly includes the Arabic tashkeel/harakat block (`\u064B-\u065F`, i.e. fatha/damma/kasra/shadda/sukun/tanwin) plus the Quranic superscript alef (`\u0670`) and Arabic-extended combining marks (`\u06D6-\u06E4`, etc.) — so `ignoreDiacritics: true` will match a fully-vocalized Uthmani verse against an unvocalized (or differently-vocalized) query term. — [`krisk/Fuse`, `src/helpers/diacritics.ts`](https://raw.githubusercontent.com/krisk/Fuse/main/src/helpers/diacritics.ts)
- Separately, Fuse.js's default tokenizer (used by its token-search feature) is Unicode-aware: `/[\p{L}\p{M}\p{N}_]+/gu`, and the docs state this "handles CJK, Cyrillic, Greek, **Arabic**, Hebrew, Devanagari, etc. out of the box" rather than only splitting on ASCII word boundaries. — [Fuse.js docs: Token Search](https://fusejs.io/token-search.html)
- What Fuse.js does **not** do: real morphological stemming (mapping inflected/derived Arabic word forms back to a shared root, e.g. كتب/يكتب/كاتب/مكتوب). It is fundamentally a Bitap-based edit-distance fuzzy matcher, not a linguistic analyzer — its fuzziness (`threshold`, `distance`) gives typo/near-miss tolerance, not root-based recall. No stemming feature for any language is mentioned anywhere in the Fuse.js docs or README.

**(b) Fits the fully-static constraint:** Yes, natively — it's exactly what qurescent already does today. Fuse.js is "a lightweight, zero-dependency fuzzy-search library... designed for searching small-to-medium datasets on the client side where you can't rely on a dedicated search backend." — [Fuse.js README](https://raw.githubusercontent.com/krisk/Fuse/main/README.md). No server, no build-time indexing step beyond bundling the JSON data.

**(c) Scaling to full verse text + translations, cost/perf:**

- Cost: free, MIT-licensed, zero infra (client bundle only). No paid tier for the open-source library itself (Fuse.js's maintainers separately sell a hosted "Fuse Cloud" API product, but that's opt-in and irrelevant if self-bundling client-side).
- Bundle size of the library itself is small and not the bottleneck: "Full build (Fuzzy + Extended + Logical + Token search): ~8.6 kB gzip; Basic build (fuzzy only): ~6.8 kB gzip." — [Fuse.js README, "Builds"](https://raw.githubusercontent.com/krisk/Fuse/main/README.md)
- The real bottleneck is **data payload + main-thread search time**, not Fuse.js's code size. Fuse.js's own web-workers guide gives concrete thresholds: "< 5K items — Use `Fuse`. Workers add latency. 5K–10K items — Either works. Test with your data. 10K+ items — `FuseWorker` is faster and keeps the UI responsive," benchmarked at "Fuse (single thread): 6,276ms" vs. "FuseWorker (4 workers): 1,909ms" on 100,000 documents. — [Fuse.js docs: Web Workers](https://fusejs.io/web-workers.html) (mirrored in the npm README's Web Workers section)
- The Quran is a fixed, known-size corpus: 6,236 āyāt total (per `docs/research/quran-data-static-generation.md`'s framing of the standard Quran corpus). Indexed as one record per verse with multiple translation fields on each record (Arabic text + translation-1 + translation-2 fields, rather than exploding into one row per translation), that's **6,236 records** — comfortably under Fuse.js's own "<5K use plain `Fuse`, no workers needed" guidance is *just* missed (6,236 > 5,000), landing squarely in the "5K–10K — either works, test with your data" band, not the "10K+, need `FuseWorker`" band. If translations are instead exploded into one row per (verse × translation) pair, record count multiplies by the number of translations offered and could cross into `FuseWorker` territory for many translations at once.
- Practical implication: Fuse.js can plausibly power full Quran-text + translation search client-side without a backend, but (1) the *data* (6,236 verses × Arabic text × N translation columns, as JSON shipped to the client) is the actual size cost to budget, not the search library; (2) exact-word Arabic search will still be edit-distance/diacritic-fold based, not root-based — meaningfully better than Pagefind's plain substring match (which has no diacritic folding built in for Arabic per the earlier research) but still not true Arabic stemming.

## 2. MeiliSearch

**(a) Arabic/diacritic capability:** Yes for tokenization/normalization, but explicitly **not** classic root-based stemming — and this is true of Meilisearch's model for *every* language, not just Arabic.

- Meilisearch's own tokenizer, Charabia, ships a dedicated Arabic pipeline: "**Arabic** | ✅ `ال` segmentation | ✅ compatibility decomposition + nonspacing-marks removal + Tatweel, Alef, Yeh, and Taa Marbuta normalization + Persian digits to ASCII conversion." — [`meilisearch/charabia` README, "Supported languages"](https://github.com/meilisearch/charabia) — confirmed in Meilisearch's own docs table, which lists **Segmentation** and **Normalization** columns (no "Stemming" column exists for *any* language in that table): "Arabic | Article (ال) segmentation | Decomposition, digit conversion, nonspacing-marks removal." — [Meilisearch docs: Language](https://www.meilisearch.com/docs/resources/help/language)
- "Nonspacing-marks removal" is the mechanism that strips Arabic tashkeel/diacritics during indexing/query, functionally similar in effect to Fuse.js's `ignoreDiacritics` (both key off Unicode's "Mn" nonspacing-mark category — [Unicode category Mn](https://www.compart.com/en/unicode/category/Mn), cited directly in the Charabia README).
- The `ال` (definite article "al-") segmentation is a real, Arabic-specific linguistic feature beyond what Fuse.js or Pagefind offer: Charabia splits a word like `الشجرة` ("the tree") into `ال` + `شجرة` at index time so a query for `شجرة` (tree) matches documents containing `الشجرة`, per the original feature discussion. — [`meilisearch/charabia` issue #133, "Arabic script: Implement specialized Segmenter"](https://github.com/meilisearch/charabia/issues/133) and [PR #205](https://github.com/meilisearch/charabia/pull/205)
- What's missing: true root/pattern-based Arabic stemming (e.g. treating كاتب/مكتوب/يكتب/كتاب as variants of the same trilateral root ك-ت-ب) is not implemented — Charabia's documented Arabic feature set is segmentation + normalization only, not stemming, and separately Meilisearch relies on typo-tolerant fuzzy matching (Levenshtein-based) as its general mechanism for "close" word variants across all languages, which is not root-aware for a heavily-inflected language like Quranic Arabic.

**(b) Fits the fully-static constraint:** **No — this is a real server**, and must be flagged clearly per the map's hard constraint. Meilisearch Community Edition is "a single binary with no external dependencies. You can run it on any Linux, macOS, or Windows machine, on bare metal or in containers" — i.e. a long-running daemon process that a static site's frontend calls over HTTP at query time, not a build-time index bundled into static HTML/JS. — [Meilisearch docs: Self-hosting overview](https://www.meilisearch.com/docs/resources/self_hosting/overview). There is no offline/pre-built static-index mode analogous to Pagefind or Fuse.js's in-browser index; a live Meilisearch process must be running and reachable at search time.

**(c) Cost:** The search engine itself is free/OSS (Community Edition, MIT license — "Fully open source under the MIT license... Free to use for anyone, including commercial usage." — [`meilisearch/meilisearch` GitHub README](https://github.com/meilisearch/meilisearch/)), but self-hosting it means running and paying for a server 24/7 (a VM, container host, etc.) — a real ongoing infra cost/maintenance burden the map's "no live server" constraint was written to avoid. The vendor's own managed Cloud tier (the alternative to self-hosting your own server) starts at "$30/month" usage-based or "$18/mo" per resource-based instance. — [Meilisearch Pricing](https://www.meilisearch.com/pricing). Either path (self-hosted server or paid Cloud) conflicts with the project's "no monetary motive... fully static" preferences; self-hosting is free in licensing terms but not in the "no live server" sense the map requires.

## 3. Typesense

**(a) Arabic/diacritic capability:** Yes, and unlike Meilisearch, Typesense's documented feature really is called "stemming."

- Typesense's locale table explicitly lists `ar` (Arabic) with "Right-to-left script" support, and its multilingual guide states Right-to-Left scripts (Arabic, Hebrew) get "Word segmentation without spaces... Character variant handling... Proper text direction handling... Diacritic handling... Proper collation." — [Typesense docs: Multilingual Search with Locales](https://typesense.org/docs/guide/locale.html)
- Stemming is enabled per-field via `"stem": true`, and "the language used for stemming is automatically determined from the `locale` parameter of the field" — using the **Snowball stemmer** algorithm underneath. — [Typesense docs: Stemming](https://typesense.org/docs/30.2/api/stemming.html)
- Snowball (the underlying stemming engine both Typesense and Lunr.js's language addon are built on, see §5) does have a real Arabic algorithm: "Jan 2016 - Arabic stemming algorithm contributed by Assem Chelli." — [snowballstem.org homepage](https://snowballstem.org/). Chelli's own algorithm description shows it doing genuine root-level normalization, e.g. مكتوب "the light stemmer" style, when its "root-based" mode is used: it reduces `اطفال`/`الاطفال`/`اطفالكم`/`اطفالهم` (variants of "children/his children/your children") all down to `طفل` ("child"). — [`assem-ch/arabicstemmer` README](https://github.laiyagushi.com/assem-ch/arabicstemmer). Typesense's own source confirms it passes the field's `locale` straight through to the underlying `libstemmer` engine via `sb_stemmer_new(language.c_str(), ...)`, so setting `"locale": "ar", "stem": true` on a field engages this real Arabic stemmer, not just character folding. — [`typesense/typesense`, `src/stemmer_manager.cpp`](https://fossies.org/linux/typesense/src/stemmer_manager.cpp)
- Caveat: Typesense's own docs warn Snowball-style rules-based stemming "may produce unintended side effects with brand names, proper nouns, and locations" since "these rules are designed primarily for common nouns" — [Typesense docs: Stemming](https://typesense.org/docs/30.2/api/stemming.html) — worth testing against Quranic proper nouns (prophet names, place names) before trusting it uncritically for verse text.

**(b) Fits the fully-static constraint:** **No — also a real server**, same flag as Meilisearch. Typesense's own README frames it as software you "run on your own infrastructure" as "server software": "Typesense Server is **server software** and we expect users to typically run it as a separate daemon" — the README even explains the choice of GPL (not AGPL) specifically *because* Typesense is meant to run as a standalone network service, not be embedded into another program. — [`typesense/typesense` GitHub README](https://github.com/typesense/typesense). Like Meilisearch, there's no static/offline export mode; a live Typesense process must be reachable at query time.

**(c) Cost:** Self-hosted Typesense Server is GPLv3-licensed and free to run yourself, "besides of course your own infra costs" — [`typesense/typesense` README](https://github.com/typesense/typesense). The alternative managed offering, Typesense Cloud, bills "a fixed hourly cost & bandwidth charges... depending on the configuration you choose" rather than per-record/per-search — [`typesense/typesense` README](https://github.com/typesense/typesense) — i.e. still a recurring cost, and still a live server either way (self-hosted or Cloud), which is the map's actual sticking point more than the dollar cost.

## 4. Lunr.js

**(a) Arabic/diacritic capability:** Yes, via the official community addon `lunr-languages`, but Lunr.js's *core* has none of this built in.

- Lunr.js core ships with no non-English language support out of the box; the `lunr-languages` addon (by `MihaiValentin`, explicitly linked from Lunr's own official guides site) is required: "Lunr Languages is a Lunr addon that helps you search in documents written in the following languages: ... Arabic..." and is loaded via `require('lunr-languages/lunr.ar')(lunr)`. — [Lunr docs: Language Support](https://lunrjs.com/guides/language_support.html); [`MihaiValentin/lunr-languages` README](https://github.com/MihaiValentin/lunr-languages/)
- `lunr-languages` documents itself as wrapping "the stemmers for all languages, ported from snowball-js" plus per-language stopword lists — [`lunr-languages` README, "Motivation"](https://github.com/MihaiValentin/lunr-languages/blob/master/README.md?plain=1) — i.e. the same underlying Snowball algorithm family Typesense uses (§3), including the same Assem Chelli Arabic algorithm, just running client-side in JS instead of server-side in C++.
- Net effect: Lunr.js + `lunr-languages`' Arabic module gives genuine root/light-stemming for Arabic, fully client-side, no server — functionally the closest thing to "Typesense's Arabic stemming, but static-site-compatible."

**(b) Fits the fully-static constraint:** Yes. Lunr.js is explicitly a client-side/build-time static-search-index library in the same family as Pagefind conceptually (though older/simpler) — you build the index once (at build time or in a script) and ship the serialized index JSON to the browser, with no server needed at query time. This is the standard "static site search" pattern (e.g. it's what many Jekyll/Hugo static blogs use for search).

**(c) Cost:** Free/OSS. Lunr.js core and `lunr-languages` are both MIT-style open-source libraries with no paid tier, no hosted service, no infra cost beyond the static bundle size of the index. This is the cheapest/lowest-maintenance option of the three "real" search engines surveyed (Fuse.js, MeiliSearch/Typesense as servers, Lunr.js as static) that has genuine Arabic stemming, precisely because it doesn't need a server at all.

Tradeoff worth flagging honestly: `lunr-languages` is a community addon (not maintained by the Lunr.js core team), and Lunr.js's project itself has historically had a slower release cadence than Fuse.js or Pagefind — this doc doesn't verify current maintenance-activity health for either package; that would need its own check before adoption, not assumed from this research pass.

## 5. Purpose-built Quran/Arabic search tooling

**Quran.com (Quran Foundation API), checked because it's the most prominent open-source-adjacent Quran app:**

- Quran.com's *current* search is a backend-only API call, not a client-side technique to crib from: "Search requires additional permission in Developer Console... Do not call Search from `@quranjs/api/public`. Search is server-side for confidential clients." — [Quran Foundation API docs: JS SDK, Search API](https://api-docs.quran.foundation/docs/sdk/javascript/search/). Their own developer-facing SDK table marks the Search API family as `Backend required? Yes` — [Quran Foundation API docs: SDK entrypoint guide](https://api-docs.quran.com/docs/sdk/javascript/).
- Quran.com's own public GitHub org confirms the underlying engine, at least for the previous-generation Rails backend: the API repo's README states plainly "Elasticsearch — The search engine used to query the Quran," with setup instructions for running an Elasticsearch cluster, creating custom index mappings per translation, and even a note about a custom `arabic_synonyms.txt` analyzer file needed on the Elasticsearch server. — [`quran-api-rails` README, mirrored at `reuf/quran-api-rails`](https://github.com/reuf/quran-api-rails) (the original `quran/quran-api-rails` repo has since been taken down — confirmed 404 as of this research — but its README is preserved verbatim in this fork, and a maintained fork under `fattain-naime/quran.com-api`, forked by an actual Quran.com core contributor (`mmahalwy`), still lists "Rails 5.0.1, Elasticsearch 5.0.1, Ruby 3.1.0" as of its most recent push (2025-12) — [`fattain-naime/quran.com-api`](https://github.com/fattain-naime/quran.com-api))
- **Takeaway:** Quran.com's own implementation, both past (Rails + Elasticsearch, self-hosted synonym files) and present (Quran Foundation's hosted Search API, backend-only), is consistently a live-server architecture. It is not a source of client-side/static techniques transferable to qurescent's constraint — it confirms, if anything, that the team building the most prominent Quran search product chose a real search-engine server (Elasticsearch) with custom Arabic synonym expansion rather than any static-index approach, because their scale/relevance needs go beyond what Fuse.js/Lunr.js style static indexes are designed for.

**Tarteel — explicitly flagged as NOT a primary-source-backed finding:**

- Tarteel AI does not publish an official engineering blog post or docs page describing its verse-matching architecture that this research could find; there is no primary source to cite for "how Tarteel implements search."
- Tarteel solves a different problem than this ticket anyway: it matches **spoken audio recitation** to the correct verse (ASR transcription → fuzzy text match against the 6,236-verse corpus), not free-text search over translated meaning or transliterated Arabic — i.e. it's a voice-recognition/alignment problem, not the "type Arabic or English words, find matching verses/translations" problem this ticket is about.
- The only evidence found is third-party, unofficial reimplementations inferred from Tarteel's public Whisper model (`tarteel-ai/whisper-base-ar-quran` on Hugging Face) — e.g. community projects doing ASR transcription followed by Levenshtein-distance fuzzy matching against the verse corpus. Because these are third-party inferences rather than Tarteel's own documentation, and because the problem domain doesn't match this ticket's question, **Tarteel is not a usable reference for this decision** and is noted here only to record that it was checked and found not applicable.

**No other Quran-specific static/client-side search library was found** with its own official documentation of an Arabic-search implementation strategy during this research pass (e.g. no primary-source hits for an "official Tanzil.net search implementation" or similar). If one exists, it wasn't surfaced by this search.

## 6. Option landscape (not a decision — that's for a future ticket)

Given the map's two hard/standing constraints — **fully static, no live server** and **no monetary motive, prefer free/low-maintenance** — the tools above sort cleanly:

- **Rule out entirely (violate the static constraint): MeiliSearch, Typesense.** Both have genuine, well-documented Arabic tokenization and (for Typesense) real root-adjacent stemming, and both are free to self-host in licensing terms — but both are live server daemons with no static/offline index mode, and their vendor-hosted alternatives are also both a live server *and* a recurring paid cost (Meilisearch Cloud from $18–30/mo, Typesense Cloud hourly-billed). They would only become viable if the map's "fully static, no SSR/live per-request API" constraint is deliberately revisited for the search feature specifically — not a decision this research makes.
- **Option A — accept Pagefind's exact-match limitation for now.** Zero additional work/dependency/bundle cost; Starlight's Cmd+K search already ships. Arabic queries only match exact word forms (no stemming), which is a real UX gap for Quranic Arabic search (heavily inflected) but may be an acceptable interim state, especially if the custom reader pages primarily rely on their own translation/verse browsing UI rather than free-text search for the Arabic text itself.
- **Option B — layer in Fuse.js for Quran-text/translation search specifically**, reusing the pattern already proven in `src/pages/index.astro`. Real diacritic-folding for Arabic (`ignoreDiacritics`, confirmed to cover Arabic tashkeel at the Unicode-range level in the actual source), Unicode-aware tokenization, zero server, zero added cost, and the Quran's fixed 6,236-verse corpus sits right at the edge of Fuse.js's own "under 10K, single-thread `Fuse` is fine or borderline — test with your data" sizing guidance (worse if translations are exploded into separate rows rather than fields on one record). Ceiling: still edit-distance fuzzy matching, not true root-based Arabic stemming — a real (if better-than-Pagefind) quality gap versus Option C.
- **Option C — layer in Lunr.js + `lunr-languages`' Arabic module for Quran-text/translation search specifically.** The only option surveyed that combines *genuine* Arabic stemming (the same Snowball/Assem-Chelli algorithm family Typesense uses server-side, running here client-side) with full compatibility with the static-site constraint and zero ongoing cost. Tradeoff: a community-maintained addon package (not Lunr.js core team), and building/shipping a static Lunr index for the full verse+translation corpus is more setup work than reusing the already-integrated Fuse.js, with its own maintenance-activity health not yet separately verified.
- **Not viable as a reference at all: Quran.com's own approach (Elasticsearch server, backend-only) and Tarteel (wrong problem domain, no primary source).** Useful only as confirmation that the "serious" prior art in this space reaches for real search-engine servers, not static indexes — which is exactly the tradeoff qurescent's map has already chosen to avoid.
